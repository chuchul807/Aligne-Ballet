# ALIGNÉ iPhone 原生应用设计

**状态：** 已确认  
**日期：** 2026-10-15  
**目标平台：** iPhone 13 及更新机型，iOS 16 及更新版本

## 1. 目标

为现有 ALIGNÉ 网页应用增加一个完整的 iPhone 原生版本。首版使用 SwiftUI 构建，支持五个现有芭蕾动作，对单张照片进行完全本机的姿态分析，并尽可能保持网页版本当前的判断结果、反馈重点和隐私边界。

首版面向开发者自己的 iPhone 安装和验证，不以 App Store 发布为目标。网站继续独立运行，iOS 开发不得改变其现有行为或部署。

## 2. 已确认的产品范围

- 支持 Arabesque、Attitude derrière、Retiré / Passé、À la seconde 和 Tendu croisé devant。
- 用户手动选择动作和支撑腿。
- 支持使用相机拍照或从系统相册选择照片。
- 只分析单张照片，不提供实时视频指导。
- 使用 SwiftUI 原生重建界面，保留 ALIGNÉ 现有的视觉风格。
- 支持简体中文和英文，默认跟随 iPhone 系统语言。
- 不创建账号，不上传照片，不保存训练历史。
- 用户可以主动把标注后的结果图片保存到系统相册。
- 最低部署目标为 iOS 16，最低性能测试设备为 iPhone 13。

## 3. 非目标

首版不包含以下功能：

- App Store、TestFlight 或其他公开分发流程；
- iPad、macOS、Android 或 Apple Watch 专用界面；
- 视频文件分析或实时相机指导；
- 云端同步、用户账户、练习历史、分析统计或远程后端；
- 新增芭蕾动作；
- 修改现有判断阈值、动作规则或反馈标准；
- 重新训练或更换姿态识别模型；
- 自动收集照片、姿态坐标或训练数据。

## 4. 技术路线

采用完整 SwiftUI 原生实现，而不是网页套壳或隐藏 WebView 分析引擎。

Google 的 `MediaPipeTasksVision` Swift Package 负责从图片中产生姿态关键点。App 内置与网站一致的 `pose_landmarker_heavy.task` 模型，并以图片模式运行。Swift 代码负责图片处理、两次检测、可靠性判断、测量、动作规则、反馈组合和标注绘制。

官方参考资料：

- <https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/ios>
- <https://developers.google.com/edge/mediapipe/solutions/setup_ios>
- <https://github.com/google-ai-edge/mediapipe-samples/tree/main/examples/pose_landmarker/ios>

## 5. 仓库与模块结构

iOS 工程位于现有仓库的独立 `ios/` 目录。网站源码保持在当前目录中，两端共享设计定义和测试基准，但不在运行时互相依赖。

```text
aligne-two-poses/
├── src/                         现有 React 网站
├── ios/
│   └── AligneBallet/
│       ├── App/                 SwiftUI 入口、依赖装配与导航
│       ├── Features/            Select、Frame、Check、Result 功能界面
│       ├── PoseDetection/       MediaPipe 适配与两次姿态检测
│       ├── Analysis/            几何、测量、质量和可靠性判断
│       ├── Rules/               通用规则和五个动作的规则
│       ├── Feedback/            反馈排序及本地化文案键
│       ├── Annotation/          骨架、编号、区域和箭头绘制
│       ├── Resources/           模型、颜色、图标和 String Catalog
│       └── Tests/               单元、集成和一致性测试
└── ...
```

模块职责保持单一。`PoseDetection` 只输出关键点，不包含芭蕾判断；`Rules` 只根据有证据的测量产生观察项；`Feedback` 不创造规则没有支持的新判断；`Annotation` 只渲染已选择的反馈及可靠结构点。

## 6. 数据流

```text
动作与支撑腿选择
    → 拍照或相册选择
    → 方向校正与尺寸标准化
    → MediaPipe 全图检测
    → 人体区域裁切
    → MediaPipe 精细检测
    → 两次检测一致性与关键点可靠性检查
    → 照片质量和动作可分析性检查
    → 几何测量
    → 通用规则与动作专属规则
    → 去重和 Top 3 反馈组合
    → 标注命令
    → SwiftUI 结果展示与可选保存
```

分析任务在后台执行。用户返回、重置或选择新照片时，当前任务失效；旧任务即使稍后结束，也不能覆盖新状态。

## 7. 原生界面流程

### 7.1 Select / 选择

- 显示五个动作、动作说明和推荐拍摄角度。
- 用户选择动作和左侧或右侧支撑腿。
- 使用原生选择控件和继续按钮，但保留网站的颜色、排版气质与留白。

### 7.2 Frame / 拍摄

- 根据动作显示正面或四分之三侧面构图指导。
- 明确提示头部、身体和脚必须完整入镜，并且只能有一人。
- 提供“拍照”和“从相册选择”两个入口。
- 使用系统相机界面和系统照片选择器。

### 7.3 Check / 检查

- 加载和分析期间显示真实状态，不显示无法准确计算的伪百分比。
- 对尺寸过小、多人入镜、身体不完整、关键部位不可见或角度不合适的照片给出可执行的重拍说明。
- 用户可以返回拍摄或重新选择照片。

### 7.4 Result / 结果

- 顶部显示带可靠骨架、编号、区域和方向箭头的标注图片。
- 显示最多三条重点反馈，并允许展开查看全身区域检查结果。
- 提供“保存图片”和“分析另一张照片”。
- 保存操作只写入标注结果，不自动保存原始照片或建立历史记录。

## 8. 本地化与可访问性

- 使用 String Catalog 管理英文和简体中文。
- 系统语言为简体中文时显示中文，其他语言环境显示英文。
- 首版不增加 App 内语言切换设置。
- 规则标识、测量和判定逻辑不包含显示文案；两种语言映射到相同的规则结果。
- 支持 Dynamic Type、VoiceOver、清晰的焦点顺序、足够大的触控区域和有意义的无障碍标签。
- 首版只支持 iPhone 竖屏，以降低图片方向、坐标变换和标注错位风险。

## 9. 分析一致性策略

### 9.1 必须保持的行为

- 使用与网站相同的 Heavy 模型。
- 图片模式的最多检测人数保持为 2，以便多人照片仍可被拒绝。
- 保留全图和裁切区域的两次检测。
- 保留现有可见度、存在度、裁切、身体链合理性和跨检测差异阈值。
- 原样迁移图片尺寸规则、质量门槛、几何公式、动作可行性条件、五套规则、去重、优先级和 Top 3 组合。
- 迁移阶段不调整芭蕾标准或反馈方向。

### 9.2 平台差异

iPhone 照片可能通过 EXIF 表达方向。进入分析坐标系之前，App 必须先把方向标准化为实际像素方向，并让预览、检测、裁切、测量和标注使用同一坐标空间。

Swift 与 JavaScript 的数值行为，以及 MediaPipe Web 与 iOS 运行时的输出，可能存在小幅差异。因此一致性测试不要求关键点逐位完全相同，而比较：

- 照片是否可分析；
- 主要测量是否在允许容差内；
- 触发的规则标识；
- Top 3 的身体区域和纠正方向；
- 标注类型和对应区域。

出现差异时，优先检查方向、缩放、裁切和坐标映射，不通过放宽规则阈值掩盖实现问题。

## 10. 错误与状态处理

App 的流程状态至少包含：等待选择、加载图片、正在分析、需要重拍、分析成功和技术失败。

- 相机或照片权限被拒绝时，解释用途并提供打开系统设置的入口。
- 图片无法解码、格式不支持、尺寸过小或内存处理失败时，提示重新选择。
- 未检测到完整人物、出现多人或证据不足时，返回需要重拍，不把它显示成技术故障。
- 模型缺失、模型初始化失败或推理异常时，显示可重试的技术错误。
- 检测和图片处理不得阻塞主线程。
- 用户替换图片或离开流程时，旧分析结果必须被忽略并释放。

## 11. 隐私与数据生命周期

- 所有图片和姿态分析均在本机完成。
- App 不包含业务网络请求、云端存储、分析统计或广告 SDK。
- 原图、标准化图、裁切图、关键点、反馈和渲染结果只保留在当前分析会话内。
- 用户重置、替换照片或退出分析流程时释放会话资源。
- 仅在用户主动点击保存并授权后，把标注结果写入系统相册。
- 优先使用系统照片选择器，避免申请整个照片库的读取权限。
- 日志只能包含错误类别、执行阶段、耗时和图片尺寸，不能包含图片内容或姿态坐标。

## 12. 性能目标

- iPhone 13、iOS 16 是最低性能验收组合。
- 使用 Heavy 模型，不因设备速度静默切换到 Lite 模型。
- 一张符合要求的标准化照片应争取在约 5 秒内完成两次检测和结果生成。
- 在 iPhone 13 上持续超过 8 秒视为需要优化。
- 分析期间界面必须响应返回和取消操作。
- 连续分析多张照片不应造成内存持续增长或被系统终止。

性能优化可以调整图片内存路径、后台队列和中间对象生命周期，但不能未经验证地改变模型、输入坐标或判断阈值。

## 13. 测试策略

### 13.1 单元测试

Swift 测试覆盖：

- 几何函数和坐标映射；
- 关键点可靠性判断；
- 照片质量和动作可分析性；
- 所有测量；
- 通用规则和五套动作规则；
- 去重、Top 3 排序和完整身体反馈；
- 标注命令生成；
- 中英文文案键完整性。

### 13.2 跨平台一致性测试

一致性测试分为两层：

1. 领域逻辑层直接向 TypeScript 和 Swift 输入相同的关键点及可靠性数据。数值测量的绝对误差不得超过 `0.000001`，规则标识、可分析状态、反馈方向和标注命令必须一致。
2. 完整图片层向 Web 和 iOS MediaPipe 运行时输入相同图片。每张参考图片的可分析状态必须一致；对于可分析图片，双方 Top 3 中至少两个“身体区域 + 纠正方向”组合必须匹配。如果某一方根据保守规则只输出一条反馈，则该条必须匹配。

五个动作都必须包含：可接受姿势、常见错误、证据不足或身体不完整，以及多人照片。

### 13.3 集成、界面与真机测试

- 集成测试覆盖五个动作从选择到结果的完整分析链路。
- UI 测试覆盖照片选择、权限拒绝、重拍、技术失败、结果保存和中英文界面。
- iOS 16 和 iOS 17 模拟器用于验证界面与业务逻辑。
- 相机、照片方向、保存、内存和性能必须在 iPhone 13 或更新真机上验证。
- 使用同一组自有或明确授权的真实照片，对比网站与 App 的可分析状态和纠正方向。

## 14. 验收标准

首版完成需同时满足：

1. iPhone 13、iOS 16 可以安装并启动 App。
2. 五个动作都能选择支撑腿，并完成拍照或相册选择到结果的流程。
3. 所有分析均在本机完成，运行时没有业务网络上传。
4. 网页中的几何、可靠性、质量、规则、反馈和标注测试都有对应的 Swift 覆盖。
5. 共用基准输入满足第 13.2 节明确规定的数值与语义一致性标准。
6. 中文和英文均无缺失文案，系统语言切换后正确显示。
7. 用户可以保存标注结果；不保存时，流程结束后不留下 App 内历史。
8. 权限拒绝、无效图片、多人图片、模型失败和用户取消均不会导致崩溃或错误状态覆盖。
9. 典型照片的分析时间达到性能目标，连续分析没有明显内存增长。
10. 现有网站的测试、构建和生产行为保持不变。

## 15. 实施边界

实施应先建立可测试的 Swift 领域模型和移植规则，再接入 MediaPipe 和 SwiftUI。不能先制作只有界面的演示版本后再补分析契约，也不能在迁移时同时调整规则。

正式实现计划将在本设计经用户复核后单独编写，并拆分为可验证的小步骤。创建工程、下载依赖、编写 Swift 代码或修改现有产品代码都不属于本设计文档阶段。
